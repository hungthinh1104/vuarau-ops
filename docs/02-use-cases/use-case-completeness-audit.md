# Use-case completeness audit

This audit asks a different question from the command and trace catalogs:
**can the depot represent the business event truthfully from first capture through
mistake, partial completion, retry and reconciliation?**

A command existing is implementation evidence. It is not proof that the business
workflow is complete. Umbrella use cases such as Supplier, Receiving, Inventory
and Delivery currently cover several distinct user goals; this document makes the
hidden slices and gaps explicit before more trace IDs or features are created.

The policy-blocked rows below refer to derived meaning or cross-dimension effect.
They do not prevent a future additive raw-evidence workflow from recording a count,
statement line, promised quantity, cost observation or Supplier observation. Such
capture is not an implementation of stocktake approval, settlement matching, COGS,
aging, reorder risk or Supplier scoring and must remain visibly separate until the
relevant field policy is closed.

## Classification

| Status                        | Meaning                                                                                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **implemented**               | A deterministic source-backed path exists and current automated evidence covers its technical contract.                              |
| **policy-blocked**            | A plausible/known depot event has no agreed cross-dimension meaning. Current software must not invent the missing business decision. |
| **missing/discovery**         | A plausible operating goal has no first-class workflow, but field evidence is still required before implementation.                  |
| **deliberately out-of-scope** | The current primitives are sufficient or the trigger has not occurred; do not build it speculatively.                                |

## Completeness test for every operational use case

A workflow is not complete merely because its happy-path command succeeds. It must
answer all five questions below or explicitly say why one does not apply:

1. **Wrong fact:** how is a mistake corrected without erasing history?
2. **Partial fact:** what happens when only part of the quantity/amount/work is complete?
3. **Repeated legitimate action:** can the worker perform the same kind of action again without reusing the previous business identity?
4. **Unknown outcome:** what is locked while the client cannot tell whether the command committed, and how is the identical intent retried?
5. **Reconciliation:** how does the owner explain the resulting money/goods/control state at the end of the shift?

## Umbrella use-case decomposition — technically closed in M23.14b

The catalog was asymmetric: Sale/Account were split by user goal while Goods and
Operations bundled independently risky actions. M23.14b now traces the implemented
slices separately without changing runtime behavior. `pnpm trace:check` also scans
normative definitions in reverse, so an unregistered UC/BR or a business rule owned
by no use case fails the build.

The decomposed surface includes:

- Supplier master lifecycle; supplier payment/reversal; supplier adjustment;
  supplier account read/reconciliation/rebuild.
- Purchase draft lifecycle; confirmation; reads; void/replacement.
- Receiving accepted stock; Receipt reversal; receiving-progress read.
- Inventory read/history; adjustment; reclassification; reconciliation/rebuild.
- Delivery draft lifecycle; dispatch; delivery acknowledgement; return;
  Sale-fulfilment read.
- Document generation; sharing/revocation; authenticated/public validation reads.
- Operations integrity; logical export; backup validation; logical restore.

The resulting map has distinct Product/Quality, Supplier money, Purchase,
Receiving, Inventory, Delivery, Document and Operations goals. It still does **not**
mechanically create one use case per procedure: a new ID is justified when actor
goal, risk, effect boundary or correction semantics differ.

## Cross-dimension blockers before a real shadow pilot

Four gaps are more dangerous than missing convenience features because current
Money Truth can be correct while Goods Truth becomes misleading, or vice versa:

- **ASM-035:** Sale replacement after prior Delivery fulfilment.
- **ASM-036:** Purchase replacement after prior Receiving. The core
  `commercial_replacement_only` strategy is implemented with workspace policy
  lineage; field validation and pilot authorization remain separate gates.
- **ASM-037:** financial/commercial consequence of a partial customer goods return.
- **ASM-038:** return of previously accepted stock to a Supplier and any payable consequence.

Until they are answered, the pilot must either prove those events do not occur in
the selected shadow-pilot scope or stop the affected workflow when one occurs. Do
not fake correction by recording physical movements that did not happen merely to
make a replacement document look fulfilled/received.

## Evidence rule

`implemented` above means repository technical evidence, not field validation.
`policy-blocked` means **do not implement a guessed default**. A contrary depot
answer can require a new canonical fact or derived read; that is precisely why the
question is recorded before M24 rather than patched after live data exists.
